## A1: BF16 の情報量を測る道具

`a1_bf16_joho.py MODEL_DIR` が、テンソルごと・種類ごと（注意・専門家・共有専門家・ルータ・埋め込み）に出す数:

- 符号・指数・仮数それぞれのエントロピー、指数を知った上での仮数、16ビットまるごと（0次の下限）
- **指数だけハフマン符号にした実長**（DFloat11 の形。符号と仮数は生のまま）→ ビット/重み
- 左隣の指数を知った上での指数（A3「隣から予測」の目安。0次との差が大きければ A3 に望みがある）

確かめ（正規乱数 σ=0.02、1M 個）: 指数 2.545 ビット、仮数 6.97、符号 1.00、DFloat 形 10.59 ビット（元の 66.2%）、左隣で予測しても 2.545（独立なので当然 0）。
DFloat11 の報告（約70%）と同じくらいの所に来るので、道具の向きは合っている。

**先に書いておく限界**: A1 が当たっても、BF16 を可逆で約11ビットにする話で、いまの頭脳（平均約1.9ビット）より6倍大きい。
**本番の大きさ・速さを直接は良くしない。** A1 の役目は「情報がどこにあるか」（指数か仮数か、種類ごとの差、隣とのつながり）を数で持つことで、A2（偏りを残す量子化）・A3（隣から予測）をやる価値があるかの判断材料。

## B1: 使われ方で専門家ごとに精度を変える道具

**形式の壁**: GGUF は 1テンソル＝1つの型で、専門家は層ごとに1つの3次元テンソル（`ffn_*_exps`）に入っている。専門家ごとに型を混ぜる形は llama.cpp に無い。
そこで2段に分けた:

1. **賢さだけを先に安く測る（今回の道具）**: 熱い型（Q2_K）と冷たい型（専門家だけ IQ1_M）の2つを量子化し、専門家ごとにどちらかの値を戻して Q8_0 の入れ物に詰め直す。
   中身の値は「混ぜた模型」と同じなので KLD・困惑度はそのまま測れる。大きさは、本当に混ぜて保存した場合を計算で出す。
2. 効いたときだけ、llama.cpp に「層ごとに熱い専門家と冷たい専門家の2つのテンソル」を足して速さを測る。

選び方（`--erabi`）は、本命の **shiyou**（層ごとに使用数の少ない順）、**zentai**（全層で層内の割合が小さい順）、対照の **rand**（無作為、種を2つ）と **hanten**（多い順＝わざと逆）。
同じ大きさの比べ相手として、専門家を一律 IQ2_XXS（2.06 ビット）にした版も作る。

### 通しの確かめ（乱数の小さな MoE。賢さの証拠ではない）

`tameshi_moe.py`（qwen3moe 形、8専門家・2層、ルータに偏りをつけた）で `hashiru.sh` を最後まで流した。KLD は BF16 の土台との差、2つの文で測った。

| 版 | 専門家 bit/重み | 冷たい側に回る字 | KLD 文1 | KLD 文2 |
|---|---:|---:|---:|---:|
| 熱い（Q2_K のまま） | 2.896 | - | 0.0976 | 0.0984 |
| 混ぜた frac=0（入れ物の確かめ） | 2.896 | 0% | 0.0977 | 0.0986 |
| 冷たい（専門家 IQ1_M） | 1.750 | - | 0.1457 | 0.1453 |
| 混ぜた frac=1（入れ物の確かめ） | 1.750 | 100% | 0.1459 | 0.1456 |
| 一律 IQ2_XXS | 2.062 | - | 0.1161 | 0.1165 |
| shiyou 0.5 | 2.323 | 18.0% | 0.0996 | 0.1002 |
| rand 0.5（種0 / 種1） | 2.323 | 38.9% / 60.8% | 0.1125 / 0.1303 | 0.1129 / 0.1292 |
| hanten 0.5 | 2.323 | 82.0% | 0.1437 | 0.1437 |

分かったこと（道具について）:
- **入れ物（Q8_0）の誤差は無視できる**: 端の frac=0・1 が熱い・冷たいとほぼ同じ KLD（差 0.0001〜0.0003）。値の相対誤差は 0.3〜0.5%。
- 選び方の順（shiyou < rand < hanten）は、仕組みが正しく働いていれば出るはずの順に並んだ。**ただし乱数の模型なので、本物で同じになる保証は無い。**

### 先に分かっている手がかり（過去の記録）

- 35B で **専門家をすべて IQ1_M** にすると PPL +24.5%（[dougu/jikken/KEKKA.md](../../dougu/jikken/KEKKA.md) の `xexq_iq1m`）、正解率も大きく落ちた。B1 の問いは「使用数の少ない専門家だけなら、その損がどれだけ縮むか」。
- 専門家を削る（0ビット）と、較正の外の領域（コード）が壊れた（RESULTS.md 実験47・48）。**1ビットにするのは、削るよりやわらかい中間**。どの領域の文で KLD を測るかが効くので、評価文は2種類以上（英語と日本語、できればコード）。

## 次にやること（本人の側か、HF が通るセッションで）

HF をつなぐには、クラウド環境の設定（セッションの題の横の環境メニュー → Edit → Network access）で、Custom にして `huggingface.co` と `*.hf.co`（`cas-bridge.xethub.hf.co` など。重みの実体はここから来る）を足す。新しいセッションから効く。

```bash
# 例: いちばん小さい MoE（32専門家・1.3B、全部で1時間前後の見込み）
LLAMA=~/llama.cpp OUT=~/kekka_53_granite THREADS=6 \
  bash experiments/53_bit_yori_shita/hashiru.sh ~/hf/granite-3.1-1b-a400m-base kousei.txt hyouka_en.txt hyouka_ja.txt
# A1 だけ（密な小さい模型）
python3 experiments/53_bit_yori_shita/a1_bf16_joho.py ~/hf/Qwen3-0.6B --out a1_qwen3_06b.json
```

- 模型の候補: B1 は **granite-3.1-1b-a400m**（32専門家・上位8、まず流れの確認）→ **OLMoE-1B-7B**（64専門家、Q8_0 の入れ物で 7GB 台）。A1 は Qwen3-0.6B と、上の MoE の専門家。
- 較正文と評価文は重ねない。土台の答え（`--kl-divergence-base`）は BF16 で取る。
- 判定: 同じ専門家 bit/重みで **shiyou の KLD が rand（種2つ）より明らかに小さく、2つの文の両方で同じ向き** なら次（OLMoE → 35B の imatrix で使用数の偏りを見る）。
  さらに、一律 IQ2_XXS（2.06）と同じ大きさになる frac で、shiyou が勝つかを見る。勝たなければ B1 はここで止める。
- 35B の使用数の偏りは、手元の imatrix があれば `b1_mazeru.py shiyou IMATRIX.gguf` で今すぐ見られる（模型は要らない）。
