# 引き継ぎ: 「ビットより下」と「全知全能の専門家＋樹形図」の研究（2026-10-05）

クラウドの Claude Code（このリポジトリを開いたセッション）向け。読む順: この紙 → [MODEL.md](../../MODEL.md) → [docs/REPRO.md](../REPRO.md) → [AGENTS.md](../../AGENTS.md)。

## 1. 今どういう状況か

- 目的は **16GB・GPU なしの Intel Mac で動く「育つ AI」**。合言葉は「早い・安い・賢い」。
- 頭脳: Qwen3.6-35B-A3B の UD-Q2_K_XL を、**層ごとに使われる順で専門家を 256→160 人に削った GGUF**（8.29GB）。
  Hugging Face の `intel-mac-local-llm`（重み＋このリポジトリの写し）に公開した。元の重みは unsloth/Qwen3.6-35B-A3B-GGUF。
- 測った数字（i7-9750H・16GB）: 常駐メモリ 8.0〜8.2GB、書く速さ 8〜9字/秒、知識25問 23/25、PC 操作41問 36〜39/41（±2問ぶれる）。
- CPU での推論は **メモリの読み出し量で速さが決まる**（帯域律速）。小さくできれば、そのまま速くなる見込みがある。

## 2. 本人の考え（研究の出発点）

1. **1文字に8ビットは要らない。モールス信号のように、よく出るものを短く、まれなものを長くすれば、もっと小さく速くなるのでは。**
   点と線を「流す・流さない」の組み合わせで表す。「ビットより下の新しい基準」を作れれば、わざわざ圧縮しなくても最初から小さい。
2. **専門家を1つの「全知全能の専門家」にまとめ、樹形図（はい／いいえの分かれ道）で、今回の頼みに要る所だけを取り出す。**
   全部を読まずに済み、専門家をまたいでまとめ直す時間も減るのでは。
3. Codex・NVIDIA API・GPU など、使える物はできるだけ使う。

## 3. もう分かっていること（この紙を書いた時点の測定）

- **いまの GGUF の2ビット記号は、ほぼ均一に出る**（記号1個あたり 1.996〜1.999 ビット、1バイトあたり 7.90〜7.97 ビット。ファイルの6か所×32MB で測った）。
  → 量子化した**後**のファイルにモールス式（ハフマン・算術符号）をかけても、**縮むのは1%未満**。良い量子化器は、もともと記号を均一に使うように作られている。
- 専門家を削ったので、**元の重み1個あたりに直すと平均約1.9ビット**（8.29GB×8 ÷ 約350億個）。「消した重み＝0ビット」はすでに使っている。
- 記憶の1マスは1ビットより小さくできない。でも「重み1個あたりの平均」は1ビットを下回れる（まとめて符号にする・偏りを使う・捨てる）。

## 4. 提案（やる順のおすすめ）

### A. モールス式（長さの変わる符号）を、効く所にかける
- **A1. 量子化する前の重みで測る**: 元の BF16 の重みは指数部の偏りが大きく、可逆のまま元の約70%の大きさ（約30%減）になるという報告がある（[DFloat11](https://github.com/LeanModels/DFloat11)。ほかに [ZipNN](https://arxiv.org/abs/2411.05239)（2024、約33%減、模型により50%超）、[Huff-LLM](https://arxiv.org/abs/2502.00922)（2025、可逆圧縮のまま推論）。
  小さい模型（Qwen3-0.6B など）で、指数部・仮数部ごとの情報量を測る。
- **A2. 偏りを残す量子化＋符号**（entropy-constrained quantization、[Chou・Lookabaugh・Gray 1989](https://doi.org/10.1109/29.17498)）: 「2ビットに均一に詰める」のをやめ、よく出る値を多めに残して符号で短くする。
  同じ平均ビットで、誤差が減るかを測る。
- **A3. 隣から予測する符号**: 重みは行・列・専門家の間で似ていることがある。前の値から次を予測し、外れた分だけ書く（文脈つき算術符号）。
  今回の測定は「1つずつ独立」の情報量なので、隣とのつながりはまだ測っていない。
- **A4. 3つの記号**: モールスは実は「点・線・間」の3つ。重みを −1・0・+1 の3値にする研究（[BitNet b1.58](https://arxiv.org/abs/2402.17764)、2024、log₂3 ≈ 1.585 ビット/重み）がある。後から3値にするのは難しいので、まず小さい模型で。
- 速さの注意: 長さの変わる符号は、ほどくのに順番に読む手間がかかる。CPU では「読む量が減る得」と「ほどく手間」の差し引きを必ず測る。

### B. ビットより下（重み1個あたり1ビット未満）
- **B1. 使われ方で精度を変える**: よく使う専門家は2ビット、めったに使わない専門家は1ビット前後（llama.cpp の IQ1_S 1.56・IQ1_M 1.75 ビット/重み）。k160 の延長（使用数は imatrix で取れる）。
- **B2. まとめて符号にする（ベクトル量子化）**: 重みの並びを見本表（コードブック）の番号で表す。[AQLM](https://arxiv.org/abs/2401.06118) は複数の見本表の足し合わせ、[QuIP#](https://arxiv.org/abs/2402.04396) はアダマール変換でならした重みに E8 格子の見本表を使う。CPU で見本表を引く速さも測る。
- **B3. 似た専門家を合わせる**: 中身の近い専門家を1つにまとめ、差分だけ持つ（提案 C ともつながる）。

### C. 全知全能の専門家＋樹形図
- 1つの大きな専門家に全部入れて毎回全部読むのが「密な模型」で、遅い。いまの MoE は「256人から毎回8人を選ぶ」形で、本人の案の半分はもう入っている。
- **樹形図で選ぶ**研究がある: Fast FeedForward（[FFF](https://arxiv.org/abs/2311.10770)、Belcak・Wattenhofer、2023）は、推論時に二分木をたどって一部のニューロンだけを使う。二分木の分かれ道で専門家を選ぶ [Hierarchical Routing MoE](https://arxiv.org/abs/1903.07756)（2019）もある。
- **C1. 手元でできる実験**: 160人を「一緒に呼ばれやすさ」で群に分け、①群を選ぶ→②群の中から選ぶ、の2段にする。
  群の専門家をメモリ上で隣に並べれば、CPU の読み出しがまとまって速くなる見込み。速さと賢さ（下の物差し）を測る。
- **C2. 頼みの段の樹形図**: 模型の外（カーネル）で「何を聞かれているか」を、はい／いいえで分け、要る道具・知識だけ渡す。カーネルの近道（`kernel/main.py`）の延長。

## 5. 進め方と終わりの判定

- まず **A1 と B1 を小さい模型で**（数時間で終わる）。効いた物だけ、35B（k160）へ。
- 判定: 同じ大きさで賢さが落ちない、または同じ賢さで小さい・速い。**1回の数字で決めない**（2回以上）。
- 物差し: 賢さは困惑度（wikitext 等）と、可能なら本番の物差し（知識25問・全41問。Mac の本人側で回す）。速さは CPU の字/秒。
- 結果は `docs/kenkyuu/` に足す。経過は短く、数字と判定を中心に。
