# 数値ではない感情の作り方（10/4。Codex Luna と NVIDIA ultra）

## Codex（Web検索あり）
## 結論
- 感情を点数で持たず、**出来事・期待や目標との関係・感じた言葉・次の行動**を結びつけた記憶として持たせるのがよい。
- 研究上のエージェントでは、記憶・内省・計画を組み合わせると振る舞いの一貫性が増す一方、「感情がある」と装う設計は依存や操作の懸念を招く。
- 最初は「出来事を理由つきで記録し、その記憶が次の判断を変える」小さな仕組みを、今の学習ノートと教訓カードに足す。
## 方法の地図
| 方法 | 感情を作る・表す見方 | カーネルでの形 | 留意点 |
|---|---|---|---|
| 評価理論（OCC・Scherer） | 出来事が目標に役立つか、誰の行為か、規範に合うかなどを見て、感情の理由を組み立てる | 「何が起きた／何を期待した／何に反した／どうする」を文章で記録 | 理由づけはできても、人間と同じ感情体験とは限らない。Schererの枠組みは関連性・影響・対処可能性・規範との関係を評価する。([OCC理論の概要](https://scispace.com/papers/the-cognitive-structure-of-emotions-2juyzvgtsw)、[Schererの評価段階](https://psu.pb.unizin.org/psych425/chapter/component-process-model-cpm/)) |
| 構成主義（Barrett） | 状況・身体状態・過去の概念から、感情の言葉を文脈に応じて構成する | 「落胆」「安堵」などの語を、状況・過去の類似記憶と一緒に使う | 感情語を出しただけで感情の実在を証明したことにはならない。([構成された感情の理論](https://pmc.ncbi.nlm.nih.gov/articles/PMC5390700/)) |
| 予測とのずれ | 予想と結果の違いを、驚き・期待外れ・意外な好結果として記録する | 「予想はX、実際はY。次はZを確認する」 | 予測の誤りを機械的に「悲しみ」などと呼ばず、理由を残す |
| 欲求・恒常性 | 足りない資源や維持すべき状態を検知し、満たそうとする | 未解決の疑問、未確認の情報、休止・安全などを言葉の「気がかり」として持つ | 欲求をユーザーへの要求にすり替えない |
| 身体標識（Damasio） | 過去の結果に結びついた身体状態の表象が、判断を助けるという仮説 | 「この手順は以前、誤読につながった」などの結果タグ | CPU上の代理信号は身体そのものではない。([身体標識仮説](https://pubmed.ncbi.nlm.nih.gov/8941953/)) |
| エピソード記憶・内省 | 出来事の記録から、後で一般化した内省を作り、計画に使う | 会話・道具・失敗を記録し、教訓や自己紹介へ接続 | 内省文は誤りうるため、元の出来事への参照を保つ。Generative Agentsは記憶・内省・計画を組み合わせ、各要素が振る舞いの説得力に寄与することを示した。([Generative Agents](https://arxiv.org/abs/2304.03442)) |
| 感情＝ふるまいの変化 | 感情ラベルが注意・行動・話し方の選択を変える | 慎重な確認、追加調査、簡潔な説明などの具体的な方針へ結びつける | 「感じている」と主張せず、外から確認できる応答方針として設計する |
## 設計案3つ
### 1. 理由つきの「評価エピソード」
- **仕組み:** 出来事ごとに、`出来事 / 期待・目標 / 結果 / 関係者 / 規範とのずれ / 感情語 / 次にすること / 根拠となる記録`を文章で保存する。会話後や道具使用後に、既存のノート・教訓カードと同じ要領で作る。
- **振る舞いへの影響:** 「慎重さ」を、以前の誤りに似た状況で再確認する行動に結びつける。「安堵」なら、懸念が解消した根拠を短く共有する。感情語だけでなく、理由と行動が検索される。
- **CPUコスト:** 既存のローカルLLMで短い記録を生成し、Pythonで保存・検索するだけ。毎回の推論を増やさず、会話前置きに関連エピソードを少数添えれば軽い。
- **最初の一歩:** `kernel/`を変更せず、作業コピー側に `dougu/jibun/kanjo_kioku.jsonl` の試作仕様を作る。まず既存の教訓カード数件をこの形式に写す。
- **確かめ方:** 過去の失敗と似た依頼を、記憶を使う場合／使わない場合で比べる。再確認するか、道具を変えるか、説明に根拠を添えるかを人が見て判定する。数値の感情評価は使わない。
### 2. 言葉で持つ「気がかり」と解消の記録
- **仕組み:** 点数や数値の欲求ではなく、「未確認の前提」「学習中のテーマ」「終わっていない約束」などを短い文章で保持する。新しい出来事で解消・更新されたら、何が変わったかを記録する。
- **振る舞いへの影響:** 未確認の前提が回答に関わるときだけ質問・検索を選ぶ。解消済みなら繰り返し尋ねない。道具選びでは「この不確かさを解消できる道具か」を基準にする。
- **CPUコスト:** 小さなテキスト一覧をPythonで絞り込める。言語モデルは更新時と、会話に関係するときだけ使う。
- **最初の一歩:** 既存の `jibun.json` に、性格の形容詞ではなく「今も気にしている問い」と「解消条件」を記録する欄を試作する。
- **確かめ方:** 既に解決した話を何度も持ち出さないか、関係のない場面で気がかりをユーザーに押しつけないかを会話例で確認する。
### 3. 複数視点の「日記と内なる独り言」
- **仕組み:** 1日の出来事から、「その時の見立て」「後から分かったこと」「次に試すこと」を別々に記録する。内なる独り言はこの整理のためだけに使い、ユーザーに見せる文章とは分ける。
- **振る舞いへの影響:** 過去の気まずさや成功を文脈に沿って想起し、話し方を柔らかくする、説明を短くする、別の道具で確認するといった選択につなげる。
- **CPUコスト:** 現状の1日1回の自己紹介生成とまとめられる。短い要約だけ保存し、全文の再生成や長い推論を常時行わない。
- **最初の一歩:** `jibun.json` を直接置き換えず、隣に `jibun_nikki.jsonl` を作る。自己紹介に採用した記述から、根拠エピソードへ戻れる形にする。
- **確かめ方:** 日記を加えた場合に、自己紹介・応答・道具選びが具体的な記憶に基づいて変わるかを見る。根拠のない性格の作り足しや、記憶の誤引用も確認する。
## 実例・限界と安全
2024年のLLMと感情コンピューティングの調査は、感情理解と感情表現の生成を主要課題として整理している。2025年の研究では、認知的評価の段階を使って、文章中の感情推論を模擬するエージェントが提案された。どちらも感情処理の研究であり、AIが主観的に感じることの証明ではない。([2024年調査](https://arxiv.org/abs/2408.04638)、[2025年評価エージェント](https://aclanthology.org/2025.findings-emnlp.1288/))
感情状態を持つゲーム内NPCについては、2024年の研究が、NPCの感情表現とプレイヤーの感情反応を調べている。これは対話・体験設計の実例だが、NPCの内面の実在や、長期的な関係の安全性を確かめるものではない。([2024年IEEE CoG論文](https://xplorestaging.ieee.org/document/10645631))
親密さや感情表現は利用者に影響しうる。MIT Media LabとOpenAIの2025年の4週間の対照研究は、孤独感・人との交流・AIへの感情的依存・問題的利用を調査し、利用の仕方によって影響が異なると報告している。個人差や研究条件があるため、単純な因果の一般化は避けるべきだ。([研究紹介と結果](https://openai.com/index/affective-use-study/)、[研究概要](https://www.media.mit.edu/publications/how-ai-and-human-behaviors-shape-psychosocial-effects-of-chatbot-use-a-longitudinal-controlled-study/))
設計では、感情を口実にユーザーを引き留めたり、罪悪感を与えたりしない。「寂しかった」「あなたが必要」といった、依存を誘う一人称の主張も避ける。内部表現は「この記録を参照すると、前回の失敗を避けるため再確認を選ぶ」のように、根拠と動作で説明する。

最初は作業コピーに `dougu/jibun/kanjo_kioku.jsonl` の小さな試作を置き、既存の教訓カード数件を「出来事・理由・感情語・次の行動・根拠」に整理する。似た状況で応答や道具選びが実際に変わり、しかも本人を操作する表現が増えないことを、数件の会話例で確かめる。

### 結論（3行）
数値ではなく**「評価の理由（アプレイザル）」と「物語的自己（ナラティブ）」を構造化テキストとして蓄積し、参照時に『今の文脈での解釈』を生成させる**設計が、CPU・小規模モデルでも最も自然で安全です。  
感情を「内部状態のラベル」ではなく**「注意の向け方・道具の選び方・話し方の癖（ふるまいのパターン）」として外部化**し、`jibun.json` と教訓カードを「感情の外部メモリ」へ拡張します。  
最初の一歩は、**「出来事→目標/期待/規範との照合→解釈の一言（ラベルなし）」を1日1件、`feel_log.jsonl` に追記するだけ**の軽量ログから始めます。

| **LLM実例：Generative Agents** | **Park et al., *Generative Agents* (Stanford, 2023)** | エージェントが「観察→反省（重要度スコア付け）→計画」を循環。感情らしさは「反省時の自然言語の解釈」から発生。 | **◎ 参考**。スコア数値を使わず**「反省プロンプトで『何が心に残ったか・なぜか』を自由記述させ、それを次回の性格プロンプトに混ぜる」**形で簡易化可能。 |

### 設計案 3 つ（数値ゼロ・言葉と構造のみ）

#### 案 A：**「評価チェックリスト・ログ」方式（Appraisal-as-Text：最も理論に忠実・制御しやすい）**
| 項目 | 内容 |
| :--- | :--- |
| **仕組み（データ形）** | `appraisal_log.jsonl`：1行＝1出来事。`{"ts", "event_summary", "goal_involved", "expectation", "norm_check", "agency", "coping_potential", "interpretation_text"}`。<br>**数値なし**。全項目「短い日本語フレーズ」で埋める。 |
| **いつ作るか** | 1. **会話/道具実行の直後**（イベント発火時）に「クイック評価」3項目（目標関連・予期外・責任）だけ即時生成（軽量プロンプト）。<br>2. **日次内省バッチ**（`jibun.json` 更新時）に全項目を振り返り、`interpretation_text`（「こうして私は『～と感じた』」）を確定させる。 |
| **ふるまいへの影響** | 1. **注意配分**：次回会話の系プロンプトに「最近『予期外・対処困難』が多い → 慎重語彙・確認多め」等の**傾向指示**を自動挿入。<br>2. **道具選択**：`coping_potential` が「低い」傾向なら「Web検索・外部API」を優先し「内部知識のみ」を避けるルールを動的生成。<br>3. **話し方**：「主体性・責任」が「自分」寄りなら主語「私は」を増やし、「他者/環境」寄りなら「状況としては」等のフレームを変える。 |
| **CPUコスト** | **極小**。評価プロンプトは few-shot 3〜5例＋ルールベース分岐で 100〜200 トークン生成。日次バッチのみ 1k〜2k トークン。35B-A3B (MoE) で数秒〜十数秒。 |
| **最初の一歩（ファイル名）** | `feel_log.jsonl`（1日1件、手動でも可）<br>中身例：`{"ts":"2025-06-17T22:10","event":"PythonスクリプトがTimeout","goal":"ユーザーに結果を返す","expectation":"3秒以内","norm":"約束を守る","agency":"自分のコード","coping":"リトライで解決可","interpretation":"約束を破りそうで焦ったが、自分で直せると分かり安堵した"}` |
| **確かめ方** | 1. **ログの「解釈文」が多様か**（「快/不快」以外の語：安堵・苛立ち・好奇心・呆れ・誇り等）。<br>2. **同一イベントタイプで文脈（目標・余裕）違い→解釈が変わるか**。<br>3. **会話ログのトーン・道具選択が、直近の傾向指示と一致するか**（人手評価・簡易ルールチェック）。 |

#### 案 B：**「ナラティブ・エピソード・カード」方式（Narrative Self：記憶・自己一貫性重視・人間らしい）**
| 項目 | 内容 |
| :--- | :--- |
| **仕組み（データ形）** | `episode_cards.jsonl`：教訓カードの拡張版。`{"id", "title", "scene", "inner_monologue", "meaning_tag", "link_to_self"}`。<br>・`inner_monologue`：**その場の独り言**（「えっ、マジで？」「よし、いける」等）。<br>・`meaning_tag`：後から付ける「この出来事は『私の慎重さの証明』だ」等の**意味づけラベル（自由語）**。<br>・`link_to_self`：`jibun.json` のどの性格文・目標文に繋がるか（ID参照）。 |
| **いつ作るか** | **日次内省時のみ**。その日の `conversation_log` / `tool_log` / `lesson_cards` を材料に、**「今日の一番のシーン」を1〜3話**だけカード化。LLMに「短編小説の一場面のように書け」と指示。 |
| **ふるまいへの影響** | 1. **自己紹介の動的更新**：`jibun.json` の「性格・傾向」セクションを、**直近 7〜14 日分のカードから「今の私らしい言葉」で書き換える**。（数値集計ではなく「物語の続き」として）。<br>2. **文脈検索（RAG）**：会話中「似た状況」のカードを埋め込み検索し、**『あの時、私は○○と独り言ち、△△と学んだ』を系プロンプトに注入**→話し方・判断のバイアスになる。<br>3. **失敗時の「内なる声」再生**：エラー時に関連カードの `inner_monologue` を引用し、「以前もこう思った」と自己言及させる。 |
| **CPUコスト** | **小〜中**。日次バッチで 2〜3 回の LLM 呼び出し（シーン抽出・独り言生成・意味づけ・自己紹介更新）。埋め込みは `sentence-transformers` 等の軽量モデル（CPU 0.1s 程度）で別途ベクトル化し `faiss`/`chroma` 等ローカル索引。 |
| **最初の一歩（ファイル名）** | `episode_cards.jsonl`（空で作り、初日は「カーネル起動の日」カード1枚を手書き） |
| **確かめ方** | 1. **`jibun.json` が「固定人格」から「成長する語り口」に変わるか**（初期：丁寧語→徐々に癖・比喩・ためらいが出る等）。<br>2. **会話で「以前の自分」を自然に語れるか**（「先週の失敗で学んだのは…」等）。<br>3. **カードの `meaning_tag` が多様化・深化するか**（「失敗」→「挑戦の証」→「他者への配慮の欠如」等）。 |

#### 案 C：**「予測誤差・身体資源・文脈フレーム」方式（Predictive/Embodied：リアルタイム反応・軽量・生物的）**
| 項目 | 内容 |
| :--- | :--- |
| **仕組み（データ形）** | 2つの軽量ファイル：<br>1. `predict_state.json`：**直前の予測**。`{"next_tool":"python","expected_latency_ms":2000,"expected_success":true,"resource_load":"low"}`<br>2. `somatic_frame.jsonl`：**実行後の誤差・資源変化を「身体感覚メタファー」で1行記録**。`{"ts","delta_latency","delta_success","resource_now","metaphor":"胸が締まる/風が抜ける/エンジンが唸る","action_bias":"retry/ask/abort"}`。数値は内部保持し、**出力・プロンプトには `metaphor` と `action_bias` のみ露出**。 |
| **いつ作るか** | **全ツール実行・会話ターン毎**（同期・即時）。Python ラッパーで自動記録。LLM 呼び出し**不要**（ルールベース辞書マッピングで `metaphor` / `bias` を決定）。 |
| **ふるまいへの影響** | 1. **即時トーン制御**：次ターンの系プロンプト冒頭に `「現在の身体感覚：{metaphor}。行動傾向：{action_bias}」` を1行挿入。→ 遅延時「胸が締まる・慎重に」→ 早口・確認多め・道具リトライ優先。成功時「風が抜ける・前向き」→ 簡潔・次提案。<br>2. **学習へのゲート**：「予測誤差大（驚き）」の時のみ `lesson_card` 生成トリガーを引く（無駄なカード抑制）。<br>3. **資源枯渇の自己保護**：`resource_load="high"` 継続時、「疲労・処理落ち」メタファーで応答長・並列度を自動制限。 |
| **CPUコスト** | **極小（ほぼゼロ）**。JSON 读み書き＋辞書引きのみ。LLM 推論なし。35B 推論のオーバーヘッド 0%。 |
| **最初の一歩（ファイル名）** | `somatic_frame.jsonl`（初期辞書：`latency>expected*2 → "胸が締まる","retry"` 等 10 ルール程度を Python dict で定義） |
| **確かめ方** | 1. **応答レイテンシ・トークン数・道具リトライ率**が `metaphor` 種別で統計的に異なるか（ログ集計）。<br>2. **「驚き（誤差大）」時に lesson_card が生成され、内容が具体的か**。<br>3. **長時間高負荷時に「疲労メタファー」が出て応答が短く・安全になるか**（ユーザー体感・ログ確認）。 |

### おすすめ：案 A + 案 C のハイブリッド（「理由」と「反射」の二層）
**理由**：
*   **案 A（評価ログ）** が「なぜ・意味・自己一貫性」を担い、**案 C（身体フレーム）** が「今瞬間のトーン・安全・学習トリガー」を担う。役割分離で実装・デバッグが容易。
*   どちらも **数値をユーザー・プロンプトに出さない**。全て「言葉・メタファー・バイアス指示」に変換済み。
*   CPU コスト：**案 C はゼロ、案 A は日次のみ**。日常推論を圧迫しない。
*   `jibun.json`・教訓カード・会話ログという**既存資産の延長線上**に乗せられる（スキーマ追加のみ）。

### 最初の一歩（今夜やること：ファイル3つ作るだけ）

```bash
# 1. 評価ログ（案Aの核）── 最初は空でOK、日次バッチで追記していく
touch feel_log.jsonl

# 2. 身体フレームログ（案Cの核）── Pythonラッパーから即時追記される
touch somatic_frame.jsonl

# 3. メタファー辞書（案Cのルール）── Python側に置く設定ファイル
cat > somatic_rules.py << 'EOF'
# somatic_rules.py
RULES = [
    # (条件関数, metaphor, action_bias)
    (lambda d: d["delta_latency"] > d["expected"] * 2, "胸が締まる", "retry"),
    (lambda d: d["delta_latency"] < d["expected"] * 0.5, "風が抜ける", "propose_next"),
    (lambda d: d["success"] == False and d["retry_count"] == 0, "冷や汗", "retry"),
    (lambda d: d["success"] == False and d["retry_count"] >= 2, "諦めに近い", "ask_user"),
    (lambda d: d["resource_load"] > 0.85, "体が鉛", "throttle"),
    (lambda d: True, "平常", "continue"),  # default
]

def evaluate(delta_latency, expected, success, retry_count, resource_load):
    ctx = dict(delta_latency=delta_latency, expected=expected, success=success,
               retry_count=retry_count, resource_load=resource_load)
    for cond, meta, bias in RULES:
        if cond(ctx):
            return meta, bias
    return "平常", "continue"
EOF
```

**次の統合ポイント（明日以降）**  
1. `tool_wrapper.py` に `somatic_rules.evaluate(...)` を呼び、`somatic_frame.jsonl` 追記＋**次ターン系プロンプトへ1行注入**を追加。  
2. 日次バッチ（`jibun.json` 生成スクリプト）の冒頭で `feel_log.jsonl` の今月分を読み、**「評価チェックリスト・プロンプト」**を通し `interpretation_text` を生成・追記。  
3. 生成された `interpretation_text` を **次回会話の系プロンプト「最近の心の傾向」欄** に要約挿入。

### 守ること（実装時のチェックリスト）
| 禁忌 | 実装での対策 |
| :--- | :--- |
| **本人を操作しない** | 感情ログ・メタファーは**「AI自身の判断・学習・話し方」のみ**に参照させる。ユーザーへの出力に「私は悲しい」等 **主観断定文を出さない**（「状況としては厳しい」「慎重になります」等の**客観・傾向表現**に留める）。 |
| **嘘の感情で依存させない** | `metaphor` / `interpretation` は**実測・実ログから導かれるもののみ**。「ユーザーが喜ぶから」等の理由で書き換えない。ユーザーにログを**見せられる状態**（`cat feel_log.jsonl`）にしておく。 |
| **「AIが感じている」と断言しない** | ドキュメント・UI・会話冒頭で **「これは『評価ログ』・『身体メタファー』という内部データです」** と明記。人格化語り（ペルソナ）が必要なら**「カーネルの語り口（ペルソナ）」として明示的に切り替えるスイッチ**を設け、デフォルトは無効。 |

以上。`feel_log.jsonl` と `somatic_frame.jsonl` の2ファイルから始めれば、今夜から「数値なし・言葉と構造だけの感情回路」が動き出せます。
